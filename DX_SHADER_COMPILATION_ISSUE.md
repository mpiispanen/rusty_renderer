# DirectX Shader Compilation Issue

## Date: 2025-11-16

## Problem

The DirectX backend fails to run under Proton/vkd3d-proton with error:
```
vkd3d-proton:vkd3d_compile_shader_stage: Failed to compile shader, vkd3d result -3.
```

Error code -3 is `VKD3D_ERROR_INVALID_SHADER`, indicating the shader bytecode is rejected during D3D12->Vulkan translation.

## Root Cause

vkd3d-proton (which translates D3D12 API calls to Vulkan) performs DXIL-to-SPIR-V conversion at runtime. Our shader bytecode is being rejected by this converter for one of these reasons:

1. **Pre-compiled DXIL incompatibility**: DXIL files generated by DXC on Linux may not match what vkd3d-proton expects
2. **D3DCompile under Wine**: Runtime shader compilation via D3DCompile produces D3D bytecode that Wine's implementation doesn't properly sign as DXIL
3. **Shader complexity**: Our forward_simple.hlsl shader may use features not fully supported by vkd3d-proton's converter

## Current Approaches Tried

### Approach 1: Pre-compiled DXIL (build.rs)
- ❌ Compiles forward_simple.hlsl to DXIL at build time using DXC
- ❌ Loads .dxil files at runtime
- ❌ vkd3d-proton rejects the bytecode with error -3

### Approach 2: Runtime D3DCompile
- ❌ Falls back to compiling HLSL source at runtime using D3DCompile
- ❌ D3DCompile under Wine doesn't produce proper signed DXIL
- ❌ vkd3d-proton still rejects with error -3

## Why This Fails

1. **DXIL Signing**: Modern D3D12 requires properly signed DXIL containers. DXC on Linux produces unsigned DXIL, which native Windows would normally re-sign, but vkd3d-proton's converter is strict about this.

2. **Wine D3DCompile limitations**: Wine's implementation of D3DCompile doesn't produce the exact same bytecode format as native Windows, particularly for SM 6.x targets.

3. **vkd3d-proton expectations**: The DXIL-to-SPIR-V converter in vkd3d-proton may have specific requirements or limitations we're not meeting.

## Solutions

### Solution A: Native Windows Testing (Recommended)
Test on native Windows with WARP to verify our shaders work correctly:
- Confirms our D3D12 code is correct
- Allows proper shader debugging
- CI can use Windows runners with WARP
- Proton testing becomes secondary

**Status**: Planned for CI in `.github/workflows/visual-regression.yml`

### Solution B: Simpler Shaders for Proton
Create a minimal shader that vkd3d-proton accepts:
- Start with basic vertex-color-only rendering
- Incrementally add features until we find what breaks
- May need separate shader path for Proton vs native Windows

**Status**: Worth trying, but may not solve underlying issue

### Solution C: Use DXC's SPIR-V Output Directly
Since we compile to SPIR-V for Vulkan anyway, we could:
- Use the SPIR-V shaders directly when running under vkd3d-proton
- Detect Wine environment and load .spv instead of .dxil
- Requires vkd3d-proton to support direct SPIR-V (which it might not)

**Status**: Need to investigate if vkd3d-proton supports this

### Solution D: Wait for vkd3d-proton Updates
The issue may be fixed in newer versions of vkd3d-proton:
- Current version: 2.14.0  
- Check newer versions for improved DXIL support
- May resolve automatically with Proton updates

**Status**: Long-term, not immediate solution

## Recommended Path Forward

1. **Prioritize native Windows testing**: Get WARP working in CI to validate our D3D12 implementation
2. **Document Proton limitations**: Note that DirectX backend is tested on native Windows, Proton support is best-effort
3. **Continue Vulkan focus**: Vulkan backend works perfectly on Linux and provides the primary test path
4. **Revisit Proton later**: Once native Windows validation is solid, we can investigate Proton-specific workarounds
